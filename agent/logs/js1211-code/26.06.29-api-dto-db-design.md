## 1. DB 설계

### 테이블 관계 요약

```
users  ──────────────────────────────────── 1:N ──> saved_places
                                                         ^
place_recommendation_histories ── 1:0..N (nullable) ─────┘
```

| 관계 | FK 위치 | 설명 |
|------|------|------|
| users → saved_places | `saved_places.user_id` | 1명의 유저가 N개 저장 가능 |
| place_recommendation_histories → saved_places | `saved_places.history_id` (NULL 허용) | 어느 추천 세션에서 저장했는지 (선택) |
| users ↔ place_recommendation_histories | `place_recommendation_histories.user_ids UUID[]` | 표준 FK 아님. 그룹 추천 지원을 위해 배열로 연결 |

### 1-1. `users`

유저 계정 정보.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `id` | UUID | PK, DEFAULT gen_random_uuid() | 유저 식별자 |
| `email` | TEXT | UNIQUE, NOT NULL | 로그인용 이메일 |
| `password_hash` | TEXT | NOT NULL | bcrypt 해시 |
| `nickname` | TEXT | UNIQUE, NOT NULL | 화면에 표시되는 닉네임 (변경 가능) |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 가입 일시 |

> `updated_at`은 nickname 변경 추적이 필요해지면 추가 검토.

---

### 1-2. `place_recommendation_histories`

추천 엔진 실행 기록. 로그인/비로그인 유저 모두 저장 가능. 그룹 추천 시 여러 유저 연결 지원.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `id` | UUID | PK, DEFAULT gen_random_uuid() | 기록 식별자 |
| `user_ids` | UUID[] | NOT NULL, DEFAULT '{}' | 연관된 유저 ID 목록. 비로그인이면 빈 배열, 단독이면 1개, 그룹이면 여러 개 |
| `input` | JSONB | NOT NULL | `UserInput` 스키마 그대로 저장 |
| `output` | JSONB | NULL | `UserOutput` 스키마 그대로 저장. 에러면 NULL |
| `error_code` | TEXT | NULL | 엔진 에러 코드 (예: `DISCOVER_SEEDS_EXHAUSTED`) |
| `error_message` | TEXT | NULL | 엔진 에러 메시지 |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 요청 일시 |

> **input/output 타입**: `packages/recommendation-engine`의 `UserInput`, `UserOutput` Zod 스키마 기준.
>
> **error_code/error_message**: 엔진 `EngineOutput.ERROR`의 `error: { code, message }` 구조에 매핑. `error_code`는 재시도·모니터링에 활용.
>
> **참고**: `user_ids`는 UUID 배열이라 FK 제약 직접 걸기 어려움. 앱 레이어에서 검증.
>
> **성능 메모**: `GET /api/histories` 목록에서 `recommendationCount`를 매번 `jsonb_array_length(output->'recommendations')`로 계산하면 트래픽 증가 시 부담. 필요 시 `recommendation_count INT` 컬럼으로 비정규화 검토.

---

### 1-3. `saved_places`

유저가 추천 결과에서 저장(즐겨찾기)한 장소.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `id` | UUID | PK, DEFAULT gen_random_uuid() | 저장 식별자 |
| `user_id` | UUID | NOT NULL, FK → users.id | 저장한 유저 |
| `history_id` | UUID | NULL, FK → place_recommendation_histories.id ON DELETE SET NULL | 어느 추천 세션에서 저장했는지 (선택). 히스토리 삭제 시 저장 항목은 유지됨 |
| `place_data` | JSONB | NOT NULL | `PlaceRecommendationItem` 스키마 그대로 저장 |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 저장 일시 |

> **중복 저장 정책: 덮어쓰기 (upsert)**. `UNIQUE(user_id, (place_data->>'id'))` 인덱스 + `INSERT ... ON CONFLICT DO UPDATE`.
> 같은 장소를 다시 저장하면 409 에러 없이 `place_data`, `history_id`를 최신 값으로 갱신함.
> `place_data.id`는 안정적임 (BE-2 코드 확인, 의논사항 5번 참고).

## 2. API DTO 설계

### 공통 사항

- 기존 `packages/api-contracts`의 `ApiResponse<T>` 래퍼를 그대로 사용.
- **인증 방식**: httpOnly Cookie (JWT). 로그인/회원가입 시 서버가 `Set-Cookie`로 토큰 발급. 이후 요청에서 쿠키 자동 전송.

```ts
// 성공
{ success: true, data: T }

// 실패
{ success: false, error: string }
```

---

### 2-1. 유저 관련

#### `POST /api/auth/signup` — 회원가입

**요청 Body**

```ts
{
  email: string;      // 이메일 형식
  password: string;   // 최소 8자
  nickname: string;   // 1자 이상
}
```

**응답**

- HTTP 201
- `Set-Cookie: token=...; HttpOnly; SameSite=Strict; Secure; Max-Age=...` 헤더로 JWT 발급
- `data`:

```ts
{
  user: {
    id: string;
    email: string;
    nickname: string;
  };
}
```

**에러 케이스**

| HTTP | error 메시지 예시 | 설명 |
|------|------|------|
| 400 | `"invalid input"` | 유효성 검사 실패 |
| 409 | `"email already exists"` | 이메일 중복 |
| 409 | `"nickname already exists"` | 닉네임 중복 |

---

### 2-2. 추천 기록 관련

#### `GET /api/histories` — 내 추천 기록 목록

**쿼리 파라미터**

```
?limit=20&offset=0
```

**응답 `data`**

```ts
{
  items: {
    id: string;
    input: UserInput;               // 요청 당시 입력값
    recommendationCount: number;    // output 안의 추천 결과 수
    createdAt: string;              // ISO 8601
  }[];
  total: number;
}
```

> `output` 전체를 내려주면 너무 무거우므로, 목록에서는 `recommendationCount`만 내려줌.
> 상세 조회가 필요하면 별도 엔드포인트(`GET /api/histories/:id`) 추가 검토.

---

### 2-3. 장소 저장 관련

#### `POST /api/saves` — 장소 저장

**요청 Body**

```ts
{
  placeData: PlaceRecommendationItem;   // 엔진 output의 장소 객체 그대로
  historyId?: string;                   // 어느 추천 세션에서 저장했는지 (선택)
}
```

**응답 `data`**

```ts
{
  saved: {
    id: string;
    placeData: PlaceRecommendationItem;
    createdAt: string;
  };
}
```

> 같은 장소(동일 `placeData.id`)를 다시 저장하면 에러 없이 덮어쓰기(upsert). `createdAt`은 최초 저장 시각 유지, `placeData`·`historyId`는 최신 값으로 갱신.

**에러 케이스**

| HTTP | error 메시지 예시 | 설명 |
|------|------|------|
| 400 | `"invalid input"` | 유효성 검사 실패 |

---

#### `GET /api/saves` — 저장 목록 조회

**쿼리 파라미터**

```
?limit=20&offset=0
```

**응답 `data`**

```ts
{
  items: {
    id: string;
    placeData: PlaceRecommendationItem;
    createdAt: string;
  }[];
  total: number;
}
```

---

#### `DELETE /api/saves/:id` — 저장 삭제

**응답 `data`**

```ts
{
  success: true;
}
```

**에러 케이스**

| HTTP | error 메시지 예시 | 설명 |
| 403 | `"forbidden"` | 본인이 저장한 항목이 아님 |
| 404 | `"not found"` | 존재하지 않는 항목 |
