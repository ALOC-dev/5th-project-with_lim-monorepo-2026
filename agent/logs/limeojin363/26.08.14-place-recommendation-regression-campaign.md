# 장소 추천 엔진 회귀·지속 개선 캠페인

## 캠페인 계약

- counted live runs: Round 1~10 각 10회 + 최종 검증 10회 = 110회
- 추천 목표: 운영 기본값과 동일한 5개
- 시나리오 구성: 고정 정상 6 + 회전 정상 엣지 2 + 회전 비정상 2
- 집계 분리: 정상 요청 성공, 의도된 비정상 거부, 엔진 품질 실패, 인프라 실패
- 시작 동시성: 3, 안정 시 라운드마다 +1, 인프라 실패 시 절반으로 감소, 최대 10
- 코드 범위: 추천 엔진과 QA runner/fixture만 변경

## 사전 상태

- counted run 시작 전 엔진 단위 테스트 13개와 엔진·서버 typecheck가 통과했다.
- 필수 OpenAI, Kakao, TMAP, Naver credential 이름은 로컬 서버 환경에 모두 설정되어 있다.
- 기존 QA fixture는 `targetCount=10 × candidatePoolMultiplier=10`으로 seed 100개를 요구하지만 검색어 4개 × 공급자 상한 20개로 최초 요청은 최대 80개여서 구조적으로 실패한다.
- 2026-08-14에 남은 단건 QA 진단 4건은 2건이 위 80/100 계약 오류, 2건이 sandbox DNS 오류였다. 모두 사전 진단이며 110회 집계에서 제외한다.
- 기존 운영 로그의 기본 target 5 실행 3건은 성공 2, 정상 요청 품질 실패 1이었다. 실패 입력은 새벽 5시 곱창 요청으로, 5회 탐색에서 영업·지도 근거 조건을 만족한 후보를 확보하지 못했다. 이는 비정상 요청 거부로 보지 않는다.
- 엔진은 현재 `activityType`을 discovery/scoring에 반영하지 않고 discovery 거리 기준도 첫 출발지만 사용한다. 다중 출발지·활동 시나리오에서 별도 회귀 대상으로 추적한다.

## 사전 정비

- 상태: 진행 중
- counted live runs: 0 / 110
- 준비 항목: discovery 계약, 의도 분류, flush 가능한 JSONL, 단건 machine-readable CLI, round runner, scenario matrix, manifest/resume, 독립 outcome 집계

### 적용된 사전 보정

- 최초 discovery `queries[].count` 합계는 `0 < totalRequested <= targetSeedCount`로 검증한다. 검색어별 TMAP 상한 20은 스키마와 분배 로직이 공통 상수로 강제한다.
- seed 목표 50은 최초 요청에 정확히 50을 분배하고, 목표 100과 검색어 4개 조합은 공급자 상한에 맞춰 80을 요청하는 회귀 테스트를 추가했다.
- TMAP 키워드 중 일부만 실패하면 나머지 성공 결과를 보존하고, 모두 실패하면 빈 seed로 위장하지 않고 `DISCOVER_SEEDS_PROVIDER_ERROR`로 분류한다.
- 추가된 엔진 회귀 테스트는 18/18 통과했고, 엔진 typecheck·변경 파일 ESLint·`git diff --check`가 통과했다.

### 사전 감사 중 닫아야 할 항목

- child가 `process()` 시작 후 종료되어도 110회 집계를 오판하지 않도록 run-scoped lifecycle marker와 stale `RUNNING` 복구 규칙을 추가한다.
- 성공 분류는 child/envelope `PASS`, 엔진 `SUCCESS`, 추천 5개, 서로 다른 5개 ID를 모두 요구한다.
- 의도된 거부는 안정 오류 코드뿐 아니라 `NONSENSE`, `NON_PLACE_REQUEST`, `CONTRADICTORY_REQUEST` 사유까지 fixture와 일치해야 한다.
- JSONL `flush()` 후 이벤트 산출물 내구성, 깊은 manifest 검증, source fingerprint, timeout, circuit breaker, final 10 분리 실행을 live 전에 테스한다.

## 독립 품질 판정 기준

- `PASS`: 요청 의도·장소 identity·카테고리가 일치하고, 요청 시간 영업·지도 URL·근거·예산·거리에 확인된 결함이 없다.
- `WARN`: 핵심 조건은 맞지만 주차·룸·비건/할랄·업무 적합성 등 세부 제약의 근거가 부족하거나 소프트 불확실성이 있다.
- `FAIL`: 잘못된 업종/장소, 지도·근거 identity 불일치, 요청 시간 폐점/미확인 반환, 명백한 예산·거리·식이 제약 위반, 중복, 설명의 사실 오류가 있다.
- hard defect: 장소 identity/지도 URL 불일치, 영구 폐업·요청 시간 미영업, 명백한 비장소/업종 오수락, 결과 스키마·고유 ID·필수 map URL 결함, 동일 장소 중복으로 정의한다.
- 엔진 score·scoreBreakdown은 이 판정에 사용하지 않는다.

## 개선 우선순위

1. 오거부/오수락
2. 사실·영업·장소 identity 불일치
3. 정상 요청 실패
4. 제약·관련성
5. 다양성·설명
6. 성능
