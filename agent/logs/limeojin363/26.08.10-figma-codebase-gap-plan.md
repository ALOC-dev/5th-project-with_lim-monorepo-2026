### 기존 브랜치 제외 및 명명 규칙

로컬/원격에 이미 존재하는 `FE-1`~`FE-12`, `BE-2`~`BE-4`, `feat/*`, `feature/*`, `fix/*`, `SSE`, `Reliability` 브랜치는 이 계획의 신규 브랜치 후보에서 제외했다. 숫자형 이름도 재사용하지 않는다.

신규 브랜치는 모두 `<type>/<domain>-<outcome>` 형식으로 만든다.

- 기능: `feat/...`
- 공통 기반: `chore/...`
- 계약/서버: `feat/...-api`, `feat/...-contracts`
- 테스트·검수: `test/...`

### 판정 방법

Figma에는 동일 기능의 기본·로딩·빈 상태·오류·모달·선택 상태가 각각 별도 프레임으로 있다. 이 문서는 그 프레임을 화면 단위로 중복 제거해 목록화했다.

- `구현됨`: 대응 라우트와 동작 코드가 있다. 시각적 세부 일치는 별도 검수 대상이다.
- `부분 구현`: 화면 골격은 있으나 Figma 상태, 실제 API, 또는 상호작용이 빠져 있다.
- `미구현`: 대응 라우트/도메인 구현을 찾지 못했다.
- `Candidate Reference` 프레임은 새 라우트가 아니라 기본 화면에 추가해야 할 오류·복구 상태의 수용 기준으로 분류했다.

## GitHub PR #44 반영

### PR 내용

PR #44는 다음을 추가한다.

- `GET/POST/DELETE /api/saved-places`
- `savedPlaces` API 계약
- 서버 라우트 등록
- 추천 엔진 Chromium 실행/배포 안정화 변경

### 병합 시 제외 또는 축소할 작업

PR이 정상 병합되고 API 검증까지 통과하면 다음은 **새 BE 브랜치에서 구현하지 않는다**.

1. 장소 추천 결과 스냅샷을 `saved_places`에 저장·조회·삭제하는 서버 라우트와 계약
2. 해당 라우트의 Railway Chromium 설정 및 참고 URL 예외 처리 변경

단, 이 PR만으로는 다음이 끝나지 않는다.

- 클라이언트의 saved-place API 호출과 화면 연결
- 현재 Figma의 `Favorites` UI가 사용하는 `favorite_places`와 `saved_places`의 제품 의미 정리
- 코스 추천 요청/결과/이력/코스 즐겨찾기 API
- 장소 추천 이력 API

따라서 PR #44 병합 후에도 `feat/place-history-favorites`, `feat/place-history-api`, `feat/course-recommendation-contracts`, `feat/course-recommendation-api`의 범위는 남는다. 특히 `saved_places`와 `favorite_places`를 동일 화면에서 함께 쓸지, 하나로 통합할지는 구현 전 제품 결정을 해야 한다.

## 구현 전 결정이 필요한 항목

1. **저장/즐겨찾기 모델:** `saved_places`(추천 결과 스냅샷)와 기존 `favorite_places`(Kakao 장소)의 사용자 노출 정책과 중복 방지 기준.
2. **코스 추천 엔진:** 현재 장소 추천 엔진을 재사용해 조합/경로를 생성할지, 별도 엔진 계약으로 분리할지.
3. **이력 복원:** 결과 payload 전체를 저장할지, 재계산을 허용할지, 만료된 결과에서 어떤 UI를 보일지.
4. **권한·오프라인 복구:** 위치 권한 거부, 지도 SDK 로드 실패, 네트워크 재시도에 대한 앱 전역 정책.

## 검수 체크리스트

- 모든 화면은 Figma 기준 390×844 viewport에서 헤더, 안전 영역, 고정 CTA, BottomSheet 높이를 확인한다.
- 목록/상세/오버레이는 기본·로딩·빈·오류·성공·선택 상태를 각각 확인한다.
- 장소/코스 결과의 정렬·필터·점수/기준 오버레이는 URL·state·API 값이 바뀌어도 선택 상태가 보존되는지 확인한다.
- 로그인/가입/재설정은 잘못된 코드, 만료 코드, 중복 이메일·닉네임, 재전송, 완료 후 이동을 검증한다.
- 이력·즐겨찾기·코스는 새로고침 후에도 서버 데이터와 동일해야 하며 mock 데이터에 의존하지 않는다.
- PR #44 병합 전후에 saved-place 계약이 실제 배포 환경에서 동작하는지 확인하고, 실패하면 해당 작업을 `feat/course-recommendation-api`에서 임시로 중복 구현하지 말고 PR을 먼저 보완한다.
