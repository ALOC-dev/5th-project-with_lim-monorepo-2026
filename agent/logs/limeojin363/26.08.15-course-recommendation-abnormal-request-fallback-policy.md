# 코스 추천 엔진 비정상 요청·fallback 대응 정책

## 문서 목적

코스 추천 v2 기준으로 비정상 요청과 외부 의존성 실패를 분류하고, 현재 잘 대응하고 있는 축과 새로 보강해야 하는 축을 구분한다. 이 문서의 fallback은 단순히 성공 응답을 만드는 것이 아니라, 사용자의 선택·일정·예산을 바꾸지 않는 범위에서 신뢰할 수 있는 결과만 내보내는 정책을 뜻한다.

## 적용 범위

- 요청 계약: `CreateCourseV2RequestSchema`
- 후보 해석: 저장 장소, Kakao 직접 검색 장소, 중복 제거
- 엔진: 체류 시간, 도보 이동 시간, 코스 조합, LLM 큐레이션
- 서버 작업: 생성, 진행 상태, 취소, lease 복구, DB 영속화
- 클라이언트: `EMPTY`/`FAILED` 표시, 후보 제외 이유, 재시도 동선

## fallback 기본 원칙

1. **조용히 보정하지 않는다.** 날짜, 시간, 예산, 인원, 사용자가 선택한 장소를 임의로 바꾸지 않는다.
2. **검증 실패와 추정을 구분한다.** 영업시간·가격·이동 시간을 알 수 없으면 `UNKNOWN` 또는 `ESTIMATED`로 노출하고, 확인된 값처럼 표시하지 않는다.
3. **부분 열화를 우선한다.** 일부 후보나 일부 provider만 실패했다면 유효한 후보와 결정론 로직으로 진행한다.
4. **최소 상품 조건을 넘지 못하면 `EMPTY`다.** 2곳 이상의 유효한 타임라인을 만들 수 없으면 에러 코스를 조작하지 않는다.
5. **동일 입력 재시도의 성공 가능성으로 `retryable`을 판정한다.** 사용자가 조건을 바꿔야 하는 경우는 `false`, 일시적 provider·network·DB 문제는 `true`다.
6. **사용자 응답과 내부 진단을 분리한다.** 사용자에게는 안정적인 code와 문구만 노출하고 provider 원문, key, stack은 구조화 로그로만 남긴다.

| 필드 누락, 추가 필드, 잘못된 타입·좌표·시간 | 엄격한 Zod schema. 후보 2~15개, 2~8시간, 1~20명, 5,000~500,000원 등 범위를 검사한다. | job을 만들지 않고 HTTP 400 `invalid input`을 반환한다. | 동일 입력 기준 `false` | ✅ 계약 경계에서 비용 발생 전 차단한다. 다만 필드별 안내는 없다. |
| 과거 일정 또는 1년을 초과한 미래 일정 | `Asia/Seoul` offset으로 요청 시각을 만들어 POST 시점에 검사한다. | HTTP 400으로 거부하고 job·provider 호출을 만들지 않는다. | `false` | ✅ 기본 시점 검증이 있다. 단, 대기·복구 후 재검증은 추가로 필요하다. |

| 위조·오래된 직접 검색 snapshot | 서버가 Kakao ID를 다시 검색하고 정확한 ID 일치 결과만 쓴다. | 요청의 이름·좌표를 그대로 신뢰하지 않는다. Kakao 검색은 성공했지만 같은 ID가 없으면 해당 후보를 `LOOKUP_UNAVAILABLE`로 제외하고 나머지로 진행한다. provider 호출 자체가 실패하면 typed failure로 종료한다. | 일부 제외 시에는 즉시 재시도 불필요 | ✅ 신뢰 경계가 서버에 있다. |
| 삭제·손상된 저장 장소 snapshot | DB 행과 `PlaceRecommendationItemSchema`를 다시 검증한다. | 해당 후보를 `LOOKUP_UNAVAILABLE`로 제외하고 나머지 후보로 진행한다. | 다른 후보가 충분하면 불필요 | ✅ 후보 하나의 문제를 전체 실패로 확대하지 않는다. |
| 같은 장소의 중복 선택 | canonical Kakao ID, 없으면 엔진 장소 ID로 중복을 판별한다. | 한 번만 반영하고 `DUPLICATE` 이유를 남긴다. 직접 검색과 저장 장소가 겹치면 저장 장소 snapshot을 우선한다. | 불필요 | ✅ 결과 중복과 점수 왜곡을 막고 제외 이유를 보존한다. |
| 검증·중복 제거 후 고유 후보가 2개 미만 | 후보 해석 단계에서 고유 개수를 검사한다. | 엔진을 실행하지 않고 `EMPTY`로 종료하며 후보별 제외 이유를 반환한다. | 조건·후보 수정 필요 | ✅ 1곳짜리를 코스로 조작하지 않는다. |
| 영업시간·이동·체류 시간상 2곳 코스를 만들 수 없음 | 결정론 탐색 결과의 후보 pool이 빈 경우를 검사한다. | `COURSE_NO_FEASIBLE_COURSES`를 server adapter가 `EMPTY`로 변환한다. 클라이언트는 입력을 복원한 “다시 추천받기”를 제공한다. | 동일 입력 재시도보다 조건 수정 | ✅ 예상 가능한 상품 빈 결과를 시스템 장애와 구분한다. |
| TMAP key 누락, timeout, 일부·전체 경로 계측 실패 | 경로 API를 10초 timeout과 제한된 retry로 호출하고, 실측하지 못한 쌍을 식별한다. | 직선거리÷61m/분 추정으로 완전한 행렬을 만든다. `measuredTravelPairCount`, `estimatedTravelPairCount`, `travelMatrixFallbackReason`을 meta에 남긴다. | 불필요. 품질 저하 성공 | ✅ provider 장애가 전체 실패로 번지지 않는다. |
| 체류 시간 LLM 미설정·실패·이상치 | 카테고리, 가격대, 라스트오더, 인원, pace 기반 결정론 값을 먼저 만든다. LLM 값은 허용 범위로 clamp한다. | LLM 실패 시 결정론 값을 그대로 쓴다. `llmRefinedStayPlaceCount`, `stayEstimateFallbackReason`을 남긴다. | 불필요. 품질 저하 성공 | ✅ LLM이 타임라인 정합성을 깨지 못한다. |
| 큐레이션 LLM timeout·schema 불일치·존재하지 않는 course ID | schema 검증, ID allowlist, 중복 제거를 적용한다. | 전체 실패면 결정론 점수 상위 N개를 쓴다. 유효한 pick이 부족하면 결정론 후보로 채운다. 전체 fallback은 `curatedByLlm=false`와 reason을 남기지만 부분 보충은 현재 meta에서 따로 구분되지 않는다. | 불필요. 품질 저하 성공 | ✅ LLM이 새 장소·시간·이동 정보를 만들지 못한다. |
| 영업시간·가격 미확인 | 직접 검색 후보를 `UNKNOWN` 영업시간과 중립 점수로 변환하고, 가격은 카테고리 범위로 추정한다. | 영업시간 미확인을 감점하고 tradeoff를 복원한다. 가격은 API에서 `ESTIMATED`, 0~0은 `UNKNOWN`으로 표시한다. | 불필요. 불확실성 표시 | ✅ 확인하지 못한 사실을 단정하지 않는다. |
| 취소, 프로세스 재시작, SSE 연결 끊김 | `AbortSignal`, DB status, run token, 45초 lease, 15초 갱신, startup·30초 복구 poll을 사용한다. | 취소는 `CANCELLED`로 종료하고, 유효기간이 끝난 `RUNNING`은 다시 claim한다. 클라이언트는 SSE 외에 5초 REST polling으로 terminal 상태를 회수한다. | 자동 복구 가능 | ✅ 브라우저 연결이 job의 생명주기를 결정하지 않는다. |
| 과도한 후보로 인한 탐색 폭증 | API는 최대 15곳, 엔진은 최대 6 stop, frontier 2,000개, curation pool 30개, 경로 동시성 5로 제한한다. | 입력 크기와 탐색 비용을 상한 안에 둔다. | 불필요 | ✅ 알고리즘 내부의 기본 자원 상한은 있다. |
| 예상하지 못한 엔진·DB 실패 | 엔진 예외와 결과 영속화 예외를 job boundary에서 잡는다. | `COURSE_ENGINE_FAILURE` 또는 `COURSE_PERSISTENCE_FAILURE`로 안전한 문구를 보내고 내부 원문은 JSON 로그에 남긴다. | `true` | ✅ 알 수 없는 예외를 계약으로 정규화한다. |

## 새로 대응해야 하는 축

| 우선순위 | 추가할 비정상 축 | 현재 빈틈 | 제안 fallback | API·UX 결과 | 완료 기준 |
| --- | --- | --- | --- | --- | --- |
| P0 | 동일 요청 중복 제출 | 연타, 네트워크 retry, 앱 복구가 동일한 DB job과 provider 비용을 여러 번 만들 수 있다. | `Idempotency-Key` 또는 `userId + normalizedInputFingerprint`를 저장한다. 진행 중이거나 짧은 재사용 창 안의 같은 요청은 기존 `courseId`를 반환한다. 같은 key에 다른 body면 409다. | 중복은 새 실패가 아니며 기존 201/200 응답으로 같은 결과 화면을 연다. | 동일 key 동시 요청 N개가 DB job 1개와 provider 실행 1번만 만든다. |
| P0 | job 전체 deadline과 최대 시도 횟수 | Kakao·TMAP 개별 timeout은 있지만 전체 job deadline이 없고, process crash로 lease가 반복 만료되는 job의 시도 상한이 없다. | job에 60~90초 절대 deadline과 `maxAttemptCount=3`을 둔다. deadline은 하위 signal로 전파한다. 시도 소진 시 typed failure로 종료한다. | 일시 timeout은 `COURSE_ENGINE_UNAVAILABLE`, `retryable=true`; 반복 crash 소진은 재시도 전 운영 경보를 발생시킨다. | 어떤 job도 deadline·최대 시도를 넘어 `RUNNING`으로 남지 않는다. |
| P0 | 대기·복구 후 이미 지난 일정 | 일정은 POST 시에만 검증하므로, 오래 중단된 job이 시작 시각 후에 복구될 수 있다. | job claim 직후 provider 호출 전에 일정을 다시 검증한다. 지났으면 실행하지 않고 terminal failure로 마감한다. | 신규 `COURSE_SCHEDULE_EXPIRED`, `retryable=false`, “시간이 지나 일정을 다시 선택해 주세요.” | 복구된 과거 일정이 provider를 호출하지 않는다. |
| P0 | 과도한 요청·provider quota 고갈 | 엔진 내부 탐색 상한은 있지만 사용자·IP별 생성 rate limit, 전역 provider circuit breaker, `Retry-After`가 없다. | 사용자별 동시 job 1개, 분당 생성 횟수, provider별 circuit breaker를 둔다. circuit open 시 provider를 호출하지 않고 결정론 fallback이 안전한 단계만 진행한다. | 요청 제한은 HTTP 429 + `Retry-After`; 전체 엔진 수행이 불가하면 `COURSE_ENGINE_UNAVAILABLE`, `retryable=true`다. | 부하 테스트에서 설정한 동시성·rate를 넘지 않고 quota 신호 후 신규 provider 호출이 즉시 멈춘다. |
| P0 | 실패 code와 HTTP·SSE·UI 행동의 불일치 | 소유한 저장 장소 실패는 raw 404로 종료하지만 `COURSE_CANDIDATE_NOT_FOUND` 계약이 따로 있다. `COURSE_CANDIDATE_FORBIDDEN`, `COURSE_ROUTE_UNAVAILABLE`는 실제 경로에서 거의 사용되지 않는다. | 요청 경계와 async job에서 같은 error taxonomy를 쓴다. 사용하지 않을 code는 제거하고, 필요한 `RATE_LIMITED`, `SCHEDULE_EXPIRED`는 추가한다. | code별로 `retryable`, HTTP status, CTA를 한 테이블에서 생성한다. | 계약 테스트가 REST·SSE·DB 재조회·FE CTA의 code, message, retryable을 동시에 고정한다. |
| P1 | 후보 제외 이유의 오분류 | 계약에 `UNAVAILABLE_AT_TIME`, `OUTSIDE_TRAVEL_BUDGET`, `DURATION_LIMIT`가 있지만 현재 엔진은 성공 결과에서 주로 `INCLUDED`/`NOT_IN_TOP_COMBINATION`만 만든다. `EMPTY`는 해석된 모든 후보를 일괄 `DURATION_LIMIT`로 표시한다. | 상태 전이 탐색 시 제외된 최초 원인을 후보별로 기록한다. 영업시간, 최대 도보거리, 전체 길이, 단순 순위 탈락을 구분한다. | `EMPTY` UI는 가장 많은 원인에 맞춰 “시간 늘리기”, “먼 장소 바꾸기”, “영업 정보 확인”을 안내한다. | 각 decision code를 재현하는 엔진 테스트와 혼합 원인 우선순위 테스트가 통과한다. |
| P1 | 지리적 outlier·도보로 연결되지 않는 후보 | `maxWalkableMeters=2,000`은 경로 API 호출 여부에 주로 쓰이며, 요청 후보 집합의 연결성·outlier를 먼저 설명하지 않는다. | 직선거리 graph로 사전 검사한다. 다수 후보와 연결되지 않는 장소는 `OUTSIDE_TRAVEL_BUDGET`으로 제외하고, 2개 미만이면 `EMPTY`다. 자동으로 차량 이동으로 바꾸지 않는다. | “A는 다른 후보와 도보로 이어지기 어려워 제외했어요.” | 서울·부산 혼합 후보 테스트가 원격 장소를 제외하고 정확한 decision을 남긴다. |
| P1 | 예산 상한으로 이해한 요청 | `budgetPerPersonWon`은 현재 hard limit가 아니라 랭킹 우대 값이므로 예산을 넘는 코스도 반환될 수 있다. 필드명과 UI가 상한으로 읽히면 사용자 기대와 충돌한다. | 제품 정책을 먼저 확정한다. soft 예산이면 `targetBudgetPerPersonWon`으로 의미를 노출하고 초과를 tradeoff로 보여 준다. hard 예산이면 최소 추정 비용이 상한을 넘는 조합을 제외하고 없으면 `EMPTY`다. | soft는 “예산 초과 가능”, hard는 “예산 안에서 구성할 수 없음”으로 나눈다. | 예산 경계 앞·일치·초과 테스트가 정책별 순위와 `EMPTY`를 고정한다. |
| P1 | 새벽 넘김 일정의 영업요일 오판 | 23시 시작 + 긴 duration처럼 자정을 넘는 코스도 시작일의 `dayOfWeek`를 기준으로 영업시간을 판단할 위험이 있다. | 엔진이 날짜+시간 timeline을 사용하기 전에는 자정을 넘는 입력을 사전 거부한다. 이후에는 각 stop의 실제 날짜로 schedule을 조회한다. | 임시: `COURSE_INVALID_INPUT`, `retryable=false`, “종료 시간이 자정을 넘지 않도록 조정해 주세요.” | 요일 경계 전·후 테스트에서 잘못된 영업 판정이 없다. |
| P1 | 여러 fallback이 동시에 발생한 저신뢰 성공 | 이동 전부 추정 + 영업시간 전부 `UNKNOWN` + 체류·큐레이션 LLM fallback이 겹쳐도 `SUCCESS`는 단일 상태다. 사용자가 저하 정도를 한눈에 알기 어렵다. | 공개 quality를 `VERIFIED`, `ESTIMATED`, `DEGRADED` 중 하나로 계산하고 안정적인 `fallbackCodes[]`를 제공한다. 이동만 추정이면 결과를 제공하되 경고한다. 영업 가능성까지 전부 미확인이면 “출발 전 확인 필요”를 선택 전에 노출한다. | 결과 상단에 “이동 시간 추정”, “영업시간 미확인 N곳” 배지를 노출한다. 사용자 조건을 넘어서는 코스는 계속 `EMPTY`다. | 단일·중첩 fallback 조합별 quality·badge snapshot 테스트가 통과한다. |
| P1 | 내부 provider 에러 원문 노출 | `engineMeta` 안의 `*FallbackReason`에 `error.message`를 그대로 저장하고 API에서 `unknown`으로 반환한다. provider 응답이나 SDK 문구가 클라이언트까지 나갈 수 있다. | public meta에는 `TRAVEL_PROVIDER_UNAVAILABLE`, `STAY_MODEL_UNAVAILABLE`, `CURATION_INVALID_OUTPUT` 같은 allowlist code만 남긴다. 원문은 `courseId`, provider, stage, duration, status를 포함한 내부 로그로 이동한다. | 사용자 문구는 고정하고, 운영 로그만 상세 원인을 가진다. | provider 토큰·URL·SDK message를 심은 테스트에서 API·DB public snapshot에 원문이 없다. |
| P1 | `retryable`과 클라이언트 CTA 불일치 | FE adapter는 `retryable`을 읽지만 `FAILED`면 항상 같은 “다시 추천받기”를 노출한다. | `retryable=true`면 같은 입력 즉시 재시도, `false`면 입력 폼 복원 + 문제 필드 focus로 나눈다. `Retry-After`가 있으면 카운트다운 후 활성화한다. | 문구를 “같은 조건으로 다시 시도”와 “조건 수정하기”로 분리한다. | error code×retryable FE 순수 함수 테스트가 CTA, 문구, route state를 고정한다. |
| P2 | fallback 품질 관측 부족 | 개별 실행 meta와 로그는 있지만, 코스 추천 운영 지표·알림으로 연결되었다는 근거는 없다. | fallback code, `EMPTY` 원인, provider timeout·429, job latency, attempt count, 추정 이동 비율을 metric으로 집계한다. | 사용자 응답은 바꾸지 않고 운영 dashboard·alert를 추가한다. | provider별 fallback 비율과 `EMPTY` top reason을 배포 전후로 비교할 수 있다. |

## 최종 상태 판정표

| 조건 | 최종 상태 | 새 job 생성 | 사용자 기본 행동 |
| --- | --- | --- | --- |
| schema·시점·소유권 위반 | HTTP 400/404, job 없음 | 아니오 | 입력 또는 후보 수정 |
| idempotency key가 같은 동일 요청 | 기존 `PENDING`/`RUNNING`/terminal 재사용 | 아니오 | 기존 결과로 이동 |
| 일부 후보 실패, 유효한 후보 2개 이상 | `SUCCESS` 또는 탐색 결과에 따른 `EMPTY` | 예 | 제외 이유 확인 |
| TMAP·LLM 실패, 결정론 계산 가능 | `SUCCESS` + `ESTIMATED/DEGRADED` | 예 | fallback badge를 확인하고 결과 선택 |
| 유효한 후보 2개 미만 또는 타임라인 생성 불가 | `EMPTY` | 예 | 조건·후보 수정 |
| 일시적 provider·network·DB 장애 | `FAILED`, `retryable=true` | 예 | 같은 조건으로 재시도 |
| 시작 시간이 만료된 일정 | `FAILED`, `retryable=false` | 예 | 일정 수정 후 재요청 |
| 사용자 취소 | `CANCELLED` | 예 | 이력으로 이동 또는 새 요청 |

## 정책상 금지할 fallback

- 사용자가 선택하지 않은 장소를 자동으로 추가하지 않는다.
- 유효한 장소가 1곳뿐인데 1-stop을 코스로 반환하지 않는다.
- hard constraint로 정의된 예산이나 전체 시간을 넘긴 결과를 “근사치”로 조용히 노출하지 않는다.
- 도보 경로 실패를 차량 이동으로 임의 전환하지 않는다.
- 영업시간·가격·경로 추정을 `VERIFIED`로 표시하지 않는다.
- 다른 사용자의 저장 장소나 삭제된 snapshot을 대체 자료로 사용하지 않는다.
- LLM이 만든 새 course ID, 장소, 시간, 이동 정보를 수용하지 않는다.
- provider 원문·stack·credential 정보를 API와 SSE에 노출하지 않는다.

## 우선 구현 순서

1. **P0 계약 정렬**: error taxonomy, `retryable`, HTTP/SSE/DB/FE CTA 매핑을 한 곳으로 통합한다.
2. **P0 비용·생명주기 보호**: idempotency, user rate limit, job deadline, max attempt, 복구 시 일정 재검증을 추가한다.
3. **P1 설명 가능성**: 후보별 제외 원인을 실제 code로 분류하고 `EMPTY` CTA와 연결한다.
4. **P1 품질 계약**: public fallback code, `quality`, 중첩 fallback badge를 추가하고 내부 에러 원문을 분리한다.
5. **P2 운영 검증**: 시나리오 테스트, metric, alert로 fallback 비율과 오분류를 관리한다.

## 요약

현재 코스 추천 엔진은 **잘못된 입력의 초기 차단, 후보 단위 부분 제외, 이동·체류·LLM의 결정론 fallback, 빈 결과와 시스템 실패의 분리, job 복구**를 이미 잘 처리한다.

가장 먼저 보강할 부분은 **중복 요청 멱등성, job deadline·시도 상한, 복구 시 일정 재검증, rate limit·circuit breaker, error taxonomy와 `retryable` CTA의 일치**다. 그다음은 후보 제외 code의 실제 분류, 중첩 fallback 품질 표시, 내부 에러 원문 비공개를 적용한다.
