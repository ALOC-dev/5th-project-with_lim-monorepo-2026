# API Contracts 개발 가이드

## 목적

`@monorepo/api-contracts`는 프론트엔드와 백엔드가 공유하는 HTTP 데이터 계약의 단일 기준(SoT)이다.
이 패키지는 입력과 응답 데이터의 모양을 정의하고, 서버는 이를 경계에서 parse하며, 클라이언트는 실제 HTTP 응답을 parse한다.

현재 공개 진입점은 `packages/api-contracts/src/index.ts`다.

## 소유 경계

| 위치 | 소유하는 것 | 소유하지 않는 것 |
| --- | --- | --- |
| `packages/api-contracts/src/services/rest/*.ts` | request/query schema, response data schema, 그로부터 추론한 type | endpoint별 `ApiResponse` wrapper schema/type, HTTP handler, DB 모델 |
| `packages/api-contracts/src/core/index.ts` | 공통 `ApiResponse<T>`, `createApiResponse`, `createApiError`, `createApiResponseSchema` | 개별 endpoint의 data shape |
| `apps/server/src/routes/*.ts` | HTTP status, 인증, DB 처리, cookie, 에러 문자열, request parse | route-local 공개 request schema |
| `apps/client/src/apis/server/*.ts` | endpoint path, HTTP 호출, endpoint별 wrapper schema 조합과 parse | API data shape 재정의 |

`ApiResponse<T>` envelope는 모든 REST API가 공유하는 규칙이다.
반면 `HealthResponseSchema` 같은 endpoint별 wrapper는 `createApiResponseSchema(HealthDataSchema)`로 기계적으로 만들 수 있으므로 `api-contracts`에서 export하지 않는다.

## 현재 REST 계약

### Auth

`packages/api-contracts/src/services/rest/auth.ts`는 다음을 제공한다.

- 요청: `SignupRequestSchema`, `LoginRequestSchema`, `ForgotPasswordRequestSchema`, `ResetPasswordRequestSchema`, `SendSignupCodeRequestSchema`, `VerifySignupCodeRequestSchema`, `VerifyForgotPasswordCodeRequestSchema`
- query: `NicknameCheckQuerySchema`
- 재사용 데이터: `AuthenticatedUserSchema`
- 성공 응답 data: `AuthenticatedUserResponseDataSchema`, `LogoutResponseDataSchema`, `SendSignupCodeResponseDataSchema`, `VerifySignupCodeResponseDataSchema`, `NicknameCheckResponseDataSchema`, `ForgotPasswordResponseDataSchema`, `VerifyForgotPasswordCodeResponseDataSchema`, `ResetPasswordResponseDataSchema`

`AuthenticatedUserSchema`은 `id`, `email`, `nickname`만 포함한다. 비밀번호 hash, email 인증 상태, 생성 시각 같은 DB 내부 필드는 외부 계약에 넣지 않는다.

### Users

`packages/api-contracts/src/services/rest/users.ts`는 `UpdateMeRequestSchema`과 `DeleteCurrentUserResponseDataSchema`을 제공한다.
`GET /me`, `PATCH /me`의 성공 data는 auth의 `AuthenticatedUserResponseDataSchema`을 재사용한다.

### Health와 추천 SSE

`HealthDataSchema`은 REST health 응답의 data만 정의한다.
추천 진행 이벤트는 `services/sse/place-recommendation.ts`의 `PlaceRecommendationSseEvent`가 정의한다. SSE는 JSON REST envelope를 사용하지 않는다.

## 백엔드 작성 방식

공개 입력은 route 경계에서 shared schema로 parse한다.

```ts
import { SignupRequestSchema, createApiError } from "@monorepo/api-contracts";

const parsed = SignupRequestSchema.safeParse(req.body);
if (!parsed.success) {
  res.status(400).json(createApiError("invalid input"));
  return;
}

// parsed.data는 이후 DB/도메인 로직에 전달하는 신뢰 가능한 입력이다.
```

서버가 만드는 성공 응답은 runtime parse 대신 response data type으로 검증한다.

```ts
import {
  type AuthenticatedUserResponseData,
  createApiResponse,
} from "@monorepo/api-contracts";

res.status(200).json(
  createApiResponse({
    user: { id: user.id, email: user.email, nickname: user.nickname },
  } satisfies AuthenticatedUserResponseData),
);
```

이 방식은 DB·도메인 구현 세부사항을 계약 패키지로 옮기지 않으면서, route가 공개 응답 shape를 어기면 타입체크에서 실패하게 한다.

## 프론트엔드 작성 방식

클라이언트는 shared data schema로 endpoint별 wrapper를 해당 API 모듈 안에서 조합하고, `unknown` HTTP 응답을 parse한다.

```ts
import {
  type ApiResponse,
  createApiResponseSchema,
  HealthDataSchema,
  type HealthData,
} from "@monorepo/api-contracts";

const healthResponseSchema = createApiResponseSchema(HealthDataSchema);

const response = await serverApi.get("health").json<unknown>();
const result: ApiResponse<HealthData> = healthResponseSchema.parse(response);
```

인증 API를 클라이언트에 추가할 때도 같은 방식으로 `createApiResponseSchema(SignupResponseDataSchema)`를 API 모듈의 private 상수로 둔다.
공유 패키지에 `SignupResponseSchema`을 새로 export하지 않는다.

## 새 계약 추가 절차

1. 외부 요청 body, query, path parameter 중 소비자가 알아야 하는 값을 `services/rest/<domain>.ts`에 Zod schema로 추가한다.
2. 공개 성공 응답의 `data` 모양을 같은 파일에 `*ResponseDataSchema`으로 추가하고 `z.infer` type을 export한다.
3. server route에서 request는 `safeParse`, 성공 payload는 `satisfies`로 연결한다.
4. client API 모듈에서 `createApiResponseSchema(dataSchema)`를 조합해 응답을 parse한다.
5. core envelope, route path, HTTP status 정책, DB entity, JWT payload, 내부 서비스 입력은 공유 계약에 넣지 않는다.

## 검증 명령

계약을 바꾼 뒤 다음 명령을 실행한다.

```bash
pnpm --filter @monorepo/api-contracts typecheck
pnpm --filter @monorepo/server typecheck
pnpm --filter @monorepo/client typecheck
pnpm exec eslint packages/api-contracts/src apps/server/src/routes apps/client/src/apis/server
git diff --check
```

새 contract는 server와 client가 모두 `@monorepo/api-contracts`에서 import하며, 같은 HTTP data shape를 각 앱에서 다시 Zod로 선언하지 않아야 한다.
